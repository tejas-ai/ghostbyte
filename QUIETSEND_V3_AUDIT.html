QuietSend V3 Audit

A full read of the source in V3/ — every service, component, context, config and shipped asset — checked against what the README, PROJECT_REPORT and in-app copy claim the software does.

Version 3.0.0-PRO Stack React 19 · TypeScript · Vite · Tailwind v4 Reviewed 23 Aug 2026 Method static read, no execution

The cryptography you actually use is sound. AES-GCM-256, PBKDF2 at 600k SHA-256 rounds, random 16-byte salt and 12-byte IV per message, ECDH P-256 for the keyring — the primitives are correct and correctly parameterised. The LSB-4 and LSB-6 pixel maths round-trips cleanly, the capacity formulas agree between encoder and decoder, and the payload parsers are genuinely bounds-checked.

The problem is the distance between the code and the marketing. Several headline features do not work, and two of them cannot work — not "have a bug", but have no reachable code path at all. The docs assert verification that no test performs. For a tool aimed at journalists and researchers, that gap is the security issue: a user who trusts the Honey-Vault label is trusting something that does not exist.

Nothing here is unfixable, and most of it is a day or two of work. The list below is ordered by what I would fix first.

C1Critical

The Honey-Vault has no encoder, and its format cannot be decoded

services/stegaEngine.ts:755–812, 828–885 · components/Encoder.tsx:969 · components/Decoder.tsx:480, 597–610

Two separate failures stack here.

First, nothing calls it. encodeHoneyVault is exported and never imported by any component. The Encoder has no decoy-payload field and no second passphrase input — its label just reads "Passphrase / Honey-Vault". The Decoder reads "Passphrase / Duress Code" and renders a result.isDecoy banner. So the UI advertises duress protection end-to-end while there is no path that produces a duress container.

Second, the format is unrecoverable even if you wired it up. encodeHoneyVault fills the carrier with CSPRNG noise, places the encrypted decoy at offset 0 and the encrypted primary at totalCap − encPrimary.length. tryTrialDecrypt then tries to recover them like this:

// step 1 — decoy at offset 0
const pt = await aesDecrypt(buffer, password);   // ct = bytes 28..totalCap

// step 2 — primary, guessed from a fixed table of tail lengths
const candidateSteps = [44, 128, 256, 512, 1024, 2048, ... 2097152];
for (const step of candidateSteps) {
  const slice = buffer.subarray(buffer.length - step);
  ...
}

Step 1 hands GCM the decoy's salt and IV but a ciphertext running to the end of the buffer — hundreds of kilobytes of random padding included. The tag check fails, always. Step 2 only succeeds if encPrimary.length (which is 48 + payload bytes) happens to be one of sixteen hardcoded values — so recovering a primary payload requires it to be exactly 80, 208, 464, 976 … bytes. In practice: never.

And no test catches it. Test 7 in cryptoSelfTest.ts is named "Truly Deniable Uniform Entropy Envelope" but never calls encodeHoneyVault or tryTrialDecrypt. It hand-rolls a 2,048-byte buffer and then slices the ciphertext with subarray(28, decoyBlock.length) — using the exact length that the real decoder does not have. It validates an easier problem and reports the hard one as passing.

Fix Either build it properly or remove the labels. Building it properly means a length-free tail format the decoder can actually walk: encrypt each block, then store its length inside the authenticated plaintext and scan tail offsets by GCM tag trial at byte granularity over a bounded window (or fix both blocks at deterministic offsets derived from the passphrase). Until then, delete "Honey-Vault", "Duress Code" and the isDecoy banner from the UI, and drop the feature from the README.
C2Critical

Private keys sit unencrypted in localStorage, and back up as plaintext JSON

services/asymmetricCrypto.ts:104–105, 287–293 · components/KeyringModal.tsx:145–160

generateAsymmetricKeyPair exports the private key with exportKey('pkcs8', …), base64s it, and saveStoredKeyring writes it straight into localStorage['quietsend_keyring_v1']. Any XSS, any browser extension with host access, anyone who sits down at an unlocked machine, and any forensic image of the profile directory recovers every private key in one read. The backup button then writes the same material to quietsend_keyring_backup_<ts>.json with no encryption and no warning.

This is the sharpest contradiction in the project: the app is sold as a zero-knowledge enclave, and it stores long-term secrets in the least protected storage the browser offers.

Two smaller problems ride along. saveStoredKeyring swallows every exception, so a QuotaExceededError or storage-blocked context loses a freshly generated identity while the UI reports success. And the backup uses URL.revokeObjectURL(url) synchronously right after a.click() without appending the anchor to the DOM — which races the download in Firefox and Safari. Your own downloadBlob in stegaEngine gets both details right; this one doesn't.

Fix Wrap the private key in AES-GCM under a PBKDF2-derived vault passphrase before it touches storage, and require that passphrase to unlock the keyring for a session. Encrypt exports the same way. Surface storage failures instead of catching-and-ignoring. Reuse downloadBlob for the backup.
C3Critical

The service worker pins every user to the first version they ever loaded

public/sw.js:1–41 · index.html:47–52

The fetch handler is cache-first with no expiry and no network revalidation:

caches.match(event.request).then((cachedResponse) => {
  if (cachedResponse) return cachedResponse;   // ← always wins, forever
  return fetch(event.request).then(...)
});

CACHE_NAME is the hardcoded string 'quietsend-v3-airgap-v1', and the activate handler only deletes caches whose name differs from it. Since sw.js itself is a static file that never changes, the browser never re-runs install, the cache name never rotates, and / and /index.html are served from cache indefinitely. Your hashed asset filenames make this worse rather than better: the cached HTML keeps pointing at the old index-BWPjm3j6.js, which is also cached, so the whole stale app stays internally consistent and invisible.

Concretely: you cannot ship a security fix to anyone who has already visited the site.

Fix Version CACHE_NAME from the build (inject the commit hash), and switch the HTML/navigation request to network-first with cache fallback while keeping cache-first for hashed /assets/*. Skip cross-origin and range requests entirely — right now the handler also intercepts video range requests and can serve a full 200 from cache, which breaks seeking on your demo clips.
C4Critical

24-bit WAV carriers report success and embed nothing

services/audioStegaEngine.ts:102–104, 175–211, 275–277

parseWavHeader accepts 8, 16 and 24 bits per sample. calculateAudioCapacity then reports a real capacity for a 24-bit file, so the Encoder shows a healthy capacity meter and lets you proceed. But the write loop only handles two of the three cases:

if (header.bitsPerSample === 16)      sampleVal = outView.getInt16(...);
else if (header.bitsPerSample === 8)  sampleVal = outView.getUint8(...);
else continue;                        // 24-bit: skip, and never advance bitIdx

Every sample is skipped, bitIdx never moves, and the function returns a freshly rebuilt "clean" WAV containing zero payload bits. No error is thrown. The decoder then falls through to getUint8 for anything that isn't 16-bit, reads the wrong bytes, and reports "No valid QuietSend payload detected."

The user's experience: encode succeeds, they send the file, the recipient gets nothing. Silent data loss on a tool whose entire job is not losing the message.

Fix Reject anything that isn't 16-bit (or 8-bit) in parseWavHeader with a clear message, and add real 24-bit support later if you want it. Also add a post-encode verification pass — decode your own output before handing it to the user — so this class of bug can never ship again.
C5Critical

Encoding twice in a row fails: the cleanup effect revokes the carrier still in use

components/Encoder.tsx:193–205 · components/Comparator.tsx:252–260

Both files register a blob-URL cleanup effect with the tracked objects in the dependency array:

useEffect(() => {
  return () => {
    if (result?.startsWith('blob:'))       URL.revokeObjectURL(result);
    if (carrier?.src.startsWith('blob:'))  URL.revokeObjectURL(carrier.src);
    ...
  };
}, [result, carrier, audioCarrier]);   // ← runs on every change, not just unmount

React runs an effect's cleanup before every re-run, not only at unmount. So the moment setResult(url) fires at the end of an encode, the previous cleanup executes and revokes carrier.src — while the carrier is still loaded, still displayed, and still the input for the next encode.

The preview <img> keeps rendering because it already decoded, which hides the problem. But pressing Encode a second time calls loadCanvas(carrier.src) on a dead URL, every loader path fails, and the user gets "Failed to process image buffer on canvas. Please select a valid PNG, JPG, WebP, or BMP image." — pointing at an image that is visibly right there on screen.

Comparator has the identical bug with [orig, mod, stats, bitPlaneUrl]: running Analyze sets stats, which revokes both source images, so a second analysis fails the same way.

Fix Hold blob URLs in a ref and revoke the previous value explicitly when replacing it, with a separate useEffect(…, []) that revokes everything only on unmount. loadCarrier already revokes the old URL correctly — the effect is duplicating and mistiming that work.

H1High

The generated passphrase has ~21 bits of entropy and the meter reports ~147

services/stegaEngine.ts:380–402 · components/Encoder.tsx:64–107

generatePassphrase picks 4 words from a 38-word list. That is 38⁴ = 2,085,136 possibilities — 20.99 bits. Meanwhile calcEntropy estimates from character-class pools, so alpha-bravo-charlie-delta (25 chars, lowercase + a symbol → pool 59) scores 25 × log₂(59) ≈ 147 bits and the bar renders green with the label "Strong".

The gap is a factor of seven, and it points the wrong way — the meter is most confident exactly where the passphrase is weakest. Against PBKDF2 at 600k rounds a 2M-candidate space is a few minutes of offline GPU work per message. A user who clicks "generate" and trusts the green bar is materially less protected than one who invents their own phrase.

Secondary: n % words.length over Uint32Array introduces modulo bias, since 2³² isn't divisible by 38.

Fix Expand the list to 2,048+ words (EFF short list) and draw 6 — that's 66 bits — using rejection sampling to remove the bias. Then make the meter honest: when the passphrase came from the generator, display its known entropy rather than re-estimating it from characters, and for user-typed input use a dictionary-aware estimator (zxcvbn-style) rather than character pools.
H2High

cryptoSelfTest.ts calls an undefined function, and the build never typechecks

services/cryptoSelfTest.ts:6–14, 293, 300, 309 · package.json:8

unpackPayload is used three times in Test 6 and is not in the import list — the file imports generatePassphrase, calcSha256, crc32, buildZipArchive, parseZipArchive, zeroFill, constantTimeCompare from stegaEngine, and none of them is unpackPayload. At runtime this throws ReferenceError on the first line of the try block, gets swallowed by the catch, and Test 6 — "Decoder Bounds Checking & Fuzz Resistance" — reports failed every single time it is run.

The reason nobody noticed is the build script:

"build": "vite build"    // no tsc -b, no lint, no test

Vite transpiles with esbuild, which strips types without checking them. tsc --noEmit would fail this file with TS2304. So PROJECT_REPORT's "compiles in 624ms with zero errors and zero warnings" is true and meaningless — the compiler that would find errors never runs. generatePassphrase and calcSha256 are also imported and never used, which a linter would have flagged.

Fix Add the missing import. Change the script to "build": "tsc --noEmit && vite build", add ESLint, and add Vitest with a round-trip suite (encode→decode for LSB-4, LSB-6, WAV, GhostFile, GhostVault, asymmetric). Wire it to a GitHub Action so the gate is real.
H3High

A wrong password freezes the tab for 15–50 seconds

services/stegaEngine.ts:410–447, 854–882, 962–975, 1062–1075

When the first decrypt attempt fails, tryTrialDecrypt walks up to sixteen tail-slice candidates. Each slice starts at a different byte of the payload, so each has a different 16-byte salt — which means deriveKey's cache (keyed on password:saltHex) misses every time and runs a fresh PBKDF2 at 600,000 rounds.

On a 1 MB payload roughly 13 candidates are in range. decodeImage then does the whole thing twice — once for LSB-6, once for LSB-4 — so a single wrong password can cost 26 key derivations. At 0.5–2s each in a browser that's 15–50 seconds with no cancel button, and because PBKDF2 via SubtleCrypto isn't yielding to your worker, the tab is unresponsive throughout.

It's also an amplification primitive: one bad paste of a stego image costs the user's device a minute of CPU.

Fix Since C1 shows the tail scan cannot succeed anyway, delete it. If you rebuild deniable containers later, derive the candidate offsets from the passphrase so exactly one derivation is needed. Either way, run key derivation in a worker and give the decode button a cancel.
H4High

A worker failure hangs the encoder permanently

services/workerClient.ts:101–104, 112–148

workerInstance.onerror = () => {
  workerInstance = null;   // pendingRequests still holds an unresolved promise
};

processPixelsWithWorker returns a promise that is only settled by an onmessage with a matching id. If the worker throws — a module-worker unsupported in an older Safari, an OOM on a large carrier, a CSP refusal — onerror nulls the instance and returns. The pending promise is never resolved or rejected, encodeImage awaits forever, and the spinner runs until the user reloads. The fallbackEncode path exists but is only reachable if getWorker() returns null before the request, or if postMessage throws synchronously.

There's no timeout either, so a worker that simply never replies has the same effect.

Fix In onerror, reject or fall back every entry in pendingRequests, then clear it. Add a timeout that resolves via fallbackEncode. While you're in there: the encode path currently copies the pixel buffer twice (buffer.slice before transfer, then a fresh Uint8ClampedArray on return) — on a 4000×3000 carrier that's ~96 MB of avoidable allocation on mobile.

M1Medium

"Memory sanitization" keeps every password alive for the whole session

services/stegaEngine.ts:410–447, 139–148

keyCache is a module-level Map keyed on the literal string `${password}:${saltHex}`. Every passphrase the user types stays reachable from a live map until 20 entries accumulate or the tab closes. Meanwhile zeroFill(pwBytes) wipes a copy that was already consumed by importKey, and the original JavaScript string — immutable, possibly interned, freely copied by the GC — is untouched.

The self-test cheerfully reports "heap zeroization confirmed active". Zero-filling typed arrays in JS is a reasonable gesture, but it is not the guarantee the PROJECT_REPORT's "Side-Channel Memory Sanitization" pillar implies, and the cache actively works against it.

Fix Key the cache on a SHA-256 of the passphrase rather than the passphrase itself, cap it at 2–3 entries, and clear it on tab blur. Then soften the claim in the docs to what JS can actually offer — best-effort buffer wiping, no guarantee against memory forensics. You already added JS memory-model caveats to the deep-analysis doc; make the README match.
M2Medium

The displayed SHA-256 is a hash of the plaintext

components/Encoder.tsx:482–483, 556–562

calcSha256(rawPayload) runs before encryption, and the result is shown in the result panel with a copy button. If a user shares that hash so the recipient can verify integrity, they publish a commitment to the plaintext — anyone who can guess the message can confirm it, which is exactly the property a deniability-focused tool should not leak. It also undercuts C1's whole premise.

Fix Hash the ciphertext (or the final stego file) for the integrity display, and if you want a plaintext digest keep it local and label it clearly as "do not share".

M5Medium

The CSP permits unsafe-eval and the app can be framed

index.html:19

M9Medium

The asymmetric envelope has no sender authentication, and no HKDF

services/asymmetricCrypto.ts:1–4, 33–37, 157–207

Three things the docs get wrong about this file:

No HKDF. The header comment, README and PROJECT_REPORT all specify "ECDH P-256 + HKDF-SHA-256". The code calls deriveKey({name:'ECDH', public}, priv, {name:'AES-GCM', length:256}), which per the WebCrypto spec uses the raw shared-secret X coordinate as the AES key. No extract-and-expand, no context binding, no salt.

No sender authenticity. Ephemeral-static ECDH gives confidentiality only. Anyone holding your public key can craft a payload that decrypts cleanly and appears to come from anyone. PGP — the comparison the code invokes — signs. This is a real gap for a tool whose users receive files from untrusted channels.

64-bit fingerprints. calcKeyFingerprint truncates SHA-256 to 8 bytes. For out-of-band verification against an active MITM that's roughly 2³² work to collide — too short for the job it's doing.

Fix Run the shared secret through deriveBits → HKDF-SHA-256 with a context string, or correct the docs. Add an Ed25519 (or ECDSA P-256) signature over the ciphertext and show a verified-sender badge on decode. Widen fingerprints to 16 bytes and display them in grouped word or hex form.
